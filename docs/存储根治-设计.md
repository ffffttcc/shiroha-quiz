# 存储根治设计（P1）

目标：把 9.1 MB 题库 JSON 从 SharedPreferences 移出，启动只读 KB 级索引，题目体按需解析。
前提实测：44 库 / 5358 题，prefs 10.70 MB，`init()` 在主线程 `setContent` 前解析全部题目并逐题 `sanitizeQuestion`。
## 1. 新存储布局

```
filesDir/banks/<bankId>.json        每库一个文件，内容 = 原 banksToJson 里的单个 bank 对象
filesDir/banks/_legacy_banks.json   迁移时原样保存的旧 KEY_BANKS 全文（仅在迁移时生成）
filesDir/banks/.staging/            写盘暂存目录（rename 原子替换，失败即 deleteRecursively）
```
单库文件内容 = `banksToJson(listOf(bank))`，即只含一个 bank 对象的数组（复用现有序列化/解析，零新格式）；bank 对象字段不变。

## 2. 索引结构（新 prefs key，不改旧 key）

`KEY_BANK_INDEX` = JSON 数组，每项 `{"id","name","groupName","questionCount","version"}`（version=该库文件内容版本，用于判脏/失效）
`KEY_BANK_STORAGE_VERSION` = Int，当前 1；`0/缺失` 表示尚未迁移。

体积估算：44 项 × ~70 B ≈ 3 KB，启动解析代价可忽略；类型分布（单选/多选/判断/主观计数）不进索引：UI 现有代码是按 `bank.questions` 现算的，放进索引也得改 UI。

## 3. 启动与加载

- `init()`：读索引 → `banks` 只放 metadata（questions 为空）→ 再决定何时填题体（见 §6 两个方案）。
- `persist()`：`dirtyContentKeys` 机制保留。`KEY_BANKS` 为脏时改为：只重写「本次脏的库」文件 + 索引；不再写 9.1 MB 单值。
  新增 `dirtyBankIds`，`markBankDirty(id)` 由各库变异点（importBank/append/updateQuestion/replaceBankQuestions/updateBankInfo/deleteBank/setInk 等）打标。
- 删除库 = 删文件 + 从索引移除（`deleteBank` 已集中处理，天然适配）。

## 4. 迁移与回滚

迁移（`init()` 内，`KEY_BANK_STORAGE_VERSION < 1` 且 `KEY_BANKS` 非空时）：
1. 解析旧 `KEY_BANKS`（这一次仍要付解析+sanitize 成本，只发生一次）；
2. 逐库写 `banks/<id>.json`（先写 `.staging/` 再 rename）；
3. 写索引 + `KEY_BANK_STORAGE_VERSION=1`；
4. `KEY_BANKS` 原文转存 `_legacy_banks.json`，然后把 prefs 里 `KEY_BANKS` 置为 `""`（释放 ~9 MB XML）；
5. 任一步抛异常 → 不写版本号、不清 `KEY_BANKS`，下次启动重试（可重复执行）。

「已迁移」判据 = `KEY_BANK_STORAGE_VERSION >= 1`（不依赖旧值，允许旧值为 ""）。

**回滚步骤（旧 APK 读到 `KEY_BANKS=""` 会是空库，故必须照此退回）**：
1. 先停 App，避免迁移/写入与回滚交错。
2. 取 `files/banks/_legacy_banks.json` 全文——它就是迁移前的原 `KEY_BANKS` 值，全程未被改写。
3. 把全文写回 prefs 的 `banks` 键：`/data/data/com.reqir.shirohaquiz/shared_prefs/shiroha_quiz_native.xml` 中
   `<string name="banks">…</string>`，注意 XML 转义 `&` `<` `>`（`run-as` 或 root 下就地替换）。
4. 删除 `bank_index` 与 `bank_storage_version` 两个键（旧 APK 不认；不删也无害）。
5. 启动旧 APK，核对题库数/题数与迁移前一致；`files/banks/` 目录留着或删掉都不影响。
6. 第 3 步若失败，`_legacy_banks.json` 仍完整，重做即可，数据不会因回滚丢失。

## 5. 对备份 / 导入的影响

- 备份：`exportFullBackupZip` 从内存 `banks` 构建（现状已如此），格式与 `backup.json` 内容**完全不变**；
  唯一改动 = 导出前先保证所有库题体已加载（`ensureAllBanksLoaded()`），否则会导出空库。
- 云恢复：`replaceContentFromBackupBytes` 把「库文件 + 索引」纳入同一事务，写盘顺序钉死为
  **写 .staging → commit prefs → swap 文件**；commit 失败只丢 staging、旧文件原样 → `preferences.all`
  前后相等、旧 `banks` 元素身份不变（安全测试硬约束）。导入：`importBank` 立即写该库文件 + 更新索引。

## 6. 惰性加载（lead 已定方案 A）

**方案 A（推荐，零 UI 改动）**：`init()` 只解析索引并填 metadata；随后在后台线程逐个解析库文件、
用 `banks[i] = 完整对象` 渐进式填充 Compose 状态。启动主线程成本 ≈ 索引解析（毫秒级），题目体随后补齐。
- 优点：不碰任何 UI 文件；`banks` 语义「最终全量」不变，59 处 `.questions` 读点无需逐个审查。
- 缺点：启动后极短时间内列表题数可能显示 0，随后自动刷新；后台填充与用户操作并发时需「库未被改动才替换」的守卫。

**方案 B（未采用）**：真惰性，需改 4 个 UI 文件（BankListScreen:249/356-359/375、BankDetailScreen:168/179/234、FavoriteScreen:311、BankReviewScreen:118）读索引计数，超出 task-3 写入范围。

## 7. 对 83 单测的影响

- `testNative` 通过 `build.gradle.kts` 把 `src/androidTestNative/java` 一起编译，因此
  `QuizRepositoryCloudRestoreSafetyTest` 的 14 个用例**真在单测里跑**，且断言：
  - `preferences.all` 逐键相等（失败恢复前后、重启前后）→ 新 key 必须幂等写入，失败路径不得残留；
  - `assertSame(old, banks.single())` 对象身份不变 → 恢复失败不得替换 `banks` 元素；
  - 文件树快照相等 → `previewBackupBytes` 不得产生文件。
- 现有测试都通过 `importBank(...)` 在内存造库（`seedLocal`），写入路径走 `persist()` → 会被新存储自动落盘，
  测试断言的是 `banks`/prefs 内容而非存储实现，故预期不改测试即可绿。
- `sanitize` 从启动移到「解析该库时」：测试中库来自内存，不触发额外 sanitize，行为不变。

## 8. 提交拆分

- a) Regex 提成 `private val` 常量（`stripEmbeddedAnswerBracket` 3 个 Regex + `answerToObjectiveKeys` 1 个），纯性能，可单独回滚。
- b) 存储层 + 迁移（不含惰性）：写盘/读盘/索引/迁移/事务顺序，`init()` 仍全量加载 → 数据先搬对。
- c) 惰性加载（按 §6 选定方案）。
